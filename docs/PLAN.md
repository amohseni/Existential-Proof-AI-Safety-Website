# ∃x AI — Site Design Plan  
**Pronounced:** *ExProof AI*  
**Name meaning:** `∃x AI` = “there exists an x”; more specifically, “there exists a proof / a solution path to safe AI.”  
**Logo mark / monogram:** `∃xP`  
**Wordmark:** `∃x AI`

---

## 1. Core concept

**∃x AI** is not a generic lab website and not a personal academic page. It is a **public research interface** for a serious AI safety research group grounded in logic, epistemology, formal methods, and mathematical modeling.

The site should communicate, immediately and unmistakably, that:

1. **We are working on foundational problems in AI safety.**
2. **We use rigorous formal tools rather than generic speculation.**
3. **Our work centers on understanding agency, belief, value, interpretability, and alignment.**
4. **We are searching for a real path to safe AI.**
5. **The website itself expresses that search.**

The site should feel:

- elegant
- severe but beautiful
- highly legible
- intelligent
- minimalist
- mathematical
- EA-coded in the best sense: serious, epistemically disciplined, not performative
- Tufte-inspired in information density and clarity
- Swiss-inspired in grid, restraint, and typographic structure
- visually memorable without ever becoming “AI slop”

---

## 2. Design thesis

The visual and interaction design should embody a single idea:

> **Safe AI is not assumed; it is searched for.**

Everything on the site should support that theme.

- The **content** presents a structured research program.
- The **information architecture** shows how projects connect to core safety questions.
- The **visual language** is precise, restrained, and high-signal.
- The **background animation** represents a search through a hidden possibility space for a path to safe AI.

This is the central conceptual unifier of the whole site.

## 20. The animated background concept

This is the site’s signature visual device.

## Conceptual function
The animation represents the search for a path to safe AI through an initially unknown space of possibilities.

- The latent graph is initially invisible.
- A white “search light” explores the graph.
- Where it has already traveled, the graph becomes visible in gray.
- Sometimes there exists a complete path across the graph.
- Sometimes there does not.
- The search either:
  - finds a route and lights it green, or
  - proves there is no route and gives up
- The graph then fades away and resets

This elegantly instantiates the lab’s central theme:
> **The path is not assumed; it must be found.**

---

## 21. Background animation visual design

## Visual properties
- graph is subtle and low-contrast
- search light is the brightest moving element
- explored tree is gray
- current active position glows white
- successful full path lights green
- failure has no red “error” flash; simply graceful exhaustion
- the animation must never compete with text

## Readability constraints
- animation should sit behind the content
- under the main content column, use a very subtle dark overlay / scrim if necessary
- graph opacity should be low enough that text remains dominant
- more visible in empty margins than under dense text

## 22. Background animation mathematical setup

The user-facing requirement is:

> A binary tree generates in the background, and it should have a path from left to right with success probability exactly **1/3**.

The cleanest way to guarantee that exactly is:

## Generative model
At the beginning of each cycle:

1. Sample a hidden variable `solvable`:
   - `solvable = true` with probability `1/3`
   - `solvable = false` with probability `2/3`

2. Generate a latent binary tree embedded left-to-right across the screen.

3. If `solvable = true`:
   - choose one hidden winning branch from root to terminal depth `D`
   - ensure that branch reaches the right edge
   - generate side branches and near-miss branches around it
   - do **not** allow accidental additional complete solutions unless desired

4. If `solvable = false`:
   - generate a tree with many plausible branches and near-misses
   - ensure all branches terminate before reaching depth `D`
   - therefore there is provably no complete path to the right edge

This makes the probability of a solution path **exactly 1/3 by construction**.

That is the cleanest and most controllable implementation.

---

## 23. Tree generation details

## Graph structure
Although visually described as a binary tree, the geometry should be stylized and elegant rather than literal CS-diagram rigid.

### Parameters
- depth `D`: typically 8–11, responsive to viewport width
- root near left edge
- terminal layer near right edge
- each node has up to two children
- edges should angle gently upward/downward, not harshly
- branch spacing should be regular enough to feel mathematical, but slightly organic

## Visual embedding
The tree should visually “grow” from left to right.

Each child node advances in the x-direction.  
Vertical displacement should be controlled to prevent chaos.

### Example geometry
For node at `(x, y)`:
- child x-position = `x + dx`
- upper child y-position = `y - dy * scale`
- lower child y-position = `y + dy * scale`

Where:
- `dx` is constant or nearly constant
- `dy` decreases gradually with depth
- small jitter may be allowed, but must be subtle

This gives a clean mathematical branching form.

## 24. Smart search behavior

The searching light should feel purposeful, not random.

## Search behavior goals
- should look intelligent
- should visibly explore
- should backtrack gracefully
- should communicate “reasoned search”
- should not twitch or jitter

## Recommended search procedure
Use a **depth-first search with heuristic branch ordering**, or a **best-first search** over unexplored nodes.

### Strong recommendation
Use **heuristic DFS / best-first hybrid**:
- maintain a frontier of candidate nodes
- prefer branches that:
  - move rightward
  - preserve directional smoothness
  - have not been explored
  - appear promising geometrically

This gives the animation the feeling of a smart traversal rather than blind stumbling.

## Visual search sequence
1. begin at root
2. move along one branch
3. mark traversed edges/nodes as gray
4. if dead end, pause very briefly
5. smoothly backtrack
6. continue elsewhere
7. if goal found, illuminate full path green
8. if frontier exhausted, rest briefly, then fade out

---

## 25. Search animation states

Each cycle has five phases:

### Phase 1 — Initialization
- graph exists but is invisible
- light appears at root

### Phase 2 — Exploration
- white light moves through latent graph
- explored path becomes visible gray
- current node glows softly

### Phase 3A — Success
- if path found:
  - full successful route lights green
  - subtle pulse or sustained glow
  - maybe 1.0–1.5 second hold

### Phase 3B — Failure
- if no path exists:
  - search light stops
  - brief stillness
  - no dramatic error effect
  - only a calm recognition of exhaustion

### Phase 4 — Dissolve
- graph fades out smoothly
- traces disappear
- light disappears

### Phase 5 — Reset
- slight delay
- new graph begins

## 26. Motion design guidelines

The animation must feel elegant, not game-like.

## Motion principles
- smooth easing
- no strobing
- no abrupt jumps
- no excessive glow
- no flashy particle effects
- no noisy randomness

## Recommended motion qualities
- node-to-node movement: smooth interpolation
- short easing in and easing out
- backtracking slightly faster than forward exploration, but not noticeably so
- subtle opacity transitions for revealed edges
- long fade-out at reset

## Timing suggestions
- node traversal: ~250–550 ms depending on edge length and viewport
- dead-end pause: ~120–180 ms
- success hold: ~1200 ms
- failure hold: ~800 ms
- fade-out: ~900–1400 ms
- reset delay: ~500–900 ms

These should be tuned by feel.

## Success

- the full solution path turns green

## 36. Background animation implementation logic

Below is the conceptual algorithm.

```text
On each cycle:

1. sample solvable ~ Bernoulli(1/3)

2. create root node at left edge

3. set target depth D

4. if solvable:
   - sample one winning branch from depth 0 to D
   - generate side branches around it
   - ensure only the winning branch reaches depth D
   - other branches terminate early

5. if unsolvable:
   - generate a binary tree with many partial branches
   - ensure all branches terminate before depth D

6. hide the full graph initially

7. run search procedure:
   - start at root
   - traverse according to heuristic
   - reveal visited edges/nodes in gray
   - show current position as glowing white light
   - backtrack smoothly as needed

8. if goal found:
   - illuminate complete solution path in green
   - hold briefly

9. if all branches exhausted:
   - pause briefly

10. fade graph and search light out

11. reset and repeat
```

## 37. Heuristic scoring idea for smart traversal

If you want the search to look intelligent, give each frontier node a score like:

```text
score(node) =
  a * rightward_progress
+ b * directional_smoothness
+ c * depth_gain
- d * backtrack_penalty
+ small_random_tiebreak
```

Where:
- `rightward_progress` rewards moving toward the right edge
- `directional_smoothness` rewards visually coherent continuation
- `depth_gain` lightly rewards deeper progress
- `backtrack_penalty` slightly prefers forward exploration when comparable

This is enough to make the motion feel thoughtful.

The site should feel austere, beautiful, mathematical, and serious.
